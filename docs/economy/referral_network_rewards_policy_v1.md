# Referral & Network Rewards Policy v1

## 1. Purpose

This document defines the policy contract for referral and network Points in Go2Asia.

It fixes:

- direct referral conditional rewards;
- direct referral activity rewards;
- second-level conditional rewards;
- second-level activity rewards;
- VIP entitlement dependency;
- source-of-truth boundaries;
- terminology guardrails for participation and growth mechanics.

This document does not implement runtime behavior. It does not add API changes, migrations, UI changes, referral runtime changes, Points ledger changes, VIP entitlement runtime changes or Connect runtime changes.

## 2. Context

`docs/economy/points_policy_v1.md` defines Points as an off-chain participation currency and VIP as the primary monetization unlock for Points spending.

`docs/architecture/domain/vip_entitlement_lifecycle_contract_v1.md` defines VIP entitlement as a time-bounded spend capability and states that referral unlock and future network accrual must depend on VIP entitlement events.

Referrals are a key growth loop for VIP monetization, but referral and network rewards must remain participation mechanics inside the Points economy. They must not be framed as financial outcomes, platform obligations, partner settlement, PRO reward runtime or multi-level payout mechanics.

Current runtime only partially supports this target policy.

## 3. Core Principle

Referral and network rewards are participation incentives inside the Go2Asia Points economy. They are not income, commission, payout, passive earnings or MLM.

Реферальные и сетевые Points — это стимулы участия и роста экосистемы, а не доход, комиссия, выплата или финансовое обязательство платформы.

Policy language must focus on:

- Points за приглашение;
- Points с условиями;
- Points за активность приглашённых;
- участие сети;
- вклад в рост экосистемы;
- условия активации;
- активный VIP-период;
- начисленные Points;
- доступные Points.

## 4. Source of Truth Boundaries

Referral Service owns:

- referral codes;
- referral relations;
- referral tree facts;
- first-login activation facts;
- referral read models.

Points Service owns:

- Points ledger;
- balances;
- transactions;
- action taxonomy;
- wallet bucket projection.

VIP Entitlement owns:

- active VIP periods;
- first VIP activation facts;
- VIP expiry/revocation/refund lifecycle;
- eligibility events for unlock and accrual.

Connect owns:

- read-only projection;
- explanation UI;
- safe wallet/referral display.

Connect does not own referral graph, reward calculation, Points writes or VIP entitlement. RF is not the owner of referral rewards.

## 5. Reward Classes

### A. Direct Referral Conditional Points

Target policy:

- when a user invites a direct referral and the referral registers, the inviter receives 5000 Conditional Points;
- these Points are visible as Points with conditions;
- they unlock only after the referred user has the first active VIP entitlement;
- before unlock they must not be treated as available spend balance.

Current runtime:

- `referral_locked` is active;
- default amount is 5000 Points;
- unlock after first VIP entitlement is not active runtime.

### B. Direct Referral Activity Points

Target policy:

- the inviter receives 10% of eligible activity Points generated by the direct referral;
- this applies only while the direct referral has active VIP entitlement;
- when the direct referral VIP period ends, future accrual stops;
- inactive potential value must not be shown as already granted wallet balance.

Current runtime:

- no active producer is confirmed.

### C. Second-Level Conditional Points

Target policy:

- when a direct referral invites another user, that user is a second-level referral for the original inviter;
- the original inviter receives 100 Conditional Points;
- these Points unlock only after the second-level referral has the first active VIP entitlement.

Current runtime:

- depth-2 referral tree exists as a read model;
- second-level conditional grant is not active runtime.

### D. Second-Level Activity Points

Target policy:

- the original inviter receives 2% of eligible activity Points from the second-level referral;
- this applies only when both the direct referral and the second-level referral have active VIP entitlement;
- if either VIP period ends, future accrual stops;
- past granted ledger facts remain unchanged.

Current runtime:

- no active producer is confirmed.

### E. Technical Compensation / Correction

Future technical correction flows may exist if an implementation needs recovery semantics.

They must be treated as operational correction, not a user reward loop.

## 6. Current Runtime Reality

Current runtime facts:

- `referral_locked` exists and is active.
- The default locked referral amount is 5000 Points.
- `POST /v1/referral/claim` and internal referral link flows can create `referral_locked`.
- `/internal/referral/mark-first-login` marks activation facts but does not unlock Points.
- `referral_unlock` exists in Points action taxonomy and wallet bucket projection, but no producer is active.
- `network_accrual_level_1` and `network_accrual_level_2` exist in Points action taxonomy and wallet bucket projection, but no producers are active.
- `GET /v1/referral/tree` supports depth 1/2 as read model.
- VIP entitlement lifecycle is not active runtime yet.
- Connect reads referral and wallet projections only.

Current runtime limitation:

- wallet projection can show locked and network buckets, but target unlock/accrual policy is not fully implemented.
- `referral_locked` should not be interpreted as fully available spend value until hard spend lock and unlock events are implemented.

## 7. Target Unlock Rules

Direct referral unlock:

- unlock is triggered by the first active VIP entitlement of the referred user;
- unlock converts the direct referral Conditional Points according to Points Policy;
- unlock must be idempotent;
- unlock must not duplicate ledger rows.

Second-level unlock:

- unlock is triggered by the first active VIP entitlement of the second-level referral;
- unlock converts the second-level Conditional Points according to Points Policy;
- unlock must be idempotent;
- unlock must not duplicate ledger rows.

Unlock behavior:

- target ledger action is `referral_unlock`;
- unlock should move conditional value into available value by wallet bucket semantics;
- unlock must reference the original conditional grant and VIP entitlement event;
- unlock must not depend on Clerk role shortcuts.

## 8. Target Activity Accrual Rules

Eligible activity:

- must be defined by future implementation slices;
- must have a base Points value;
- must be safe to use as referral activity input;
- must exclude technical corrections and compensation actions unless explicitly approved.

Direct activity:

- accrual rate is 10% of eligible activity Points;
- accrual applies only during the direct referral's active VIP entitlement window;
- accrual stops for future activity when VIP expires, is revoked or is refunded.

Second-level activity:

- accrual rate is 2% of eligible activity Points;
- accrual applies only when the required direct referral and second-level referral both have active VIP entitlement;
- accrual stops for future activity when any required VIP period ends.

Past ledger facts:

- expiration, revocation or refund must not rewrite already granted ledger facts unless a separate correction policy exists;
- refund/revocation handling must be explicitly defined before implementation.

Display rule:

- inactive potential value must not appear as granted wallet balance.

## 9. Event Contract

Future event dependencies:

| Event | Producer candidate | Consumer candidate | Idempotency idea |
|---|---|---|---|
| `referral_registered` | Referral Service | Referral/Points reward orchestrator | `referral:registered:<referrerId>:<refereeId>` |
| `second_level_referral_registered` | Referral Service | Referral/Points reward orchestrator | `referral:l2:registered:<rootId>:<directId>:<secondLevelId>` |
| `vip_started` | VIP Entitlement owner | Referral Service / reward orchestrator | `vip:started:<entitlementId>` |
| `vip_expired` | VIP Entitlement owner | Referral/network accrual eligibility | `vip:expired:<entitlementId>` |
| `vip_revoked` | VIP Entitlement owner | Referral/network accrual eligibility | `vip:revoked:<entitlementId>:<effectiveAt>` |
| `vip_refunded` | VIP Entitlement owner/payment owner | Referral/network accrual eligibility | `vip:refunded:<sourceRef>` |
| `referral_points_unlocked` | Referral/Points reward orchestrator | Points Service / Connect projection | `referral:unlock:<grantExternalId>:<entitlementId>` |
| `network_points_accrued` | Referral/Points reward orchestrator | Points Service / Connect projection | `network:accrual:<level>:<activityEventId>:<beneficiaryId>` |

Safe payload fields:

- event id;
- event type;
- beneficiary user id;
- source user id;
- referral relation id or deterministic relation key;
- VIP entitlement id;
- activity event id;
- base Points amount;
- accrual Points amount;
- effective time;
- correlation id.

Forbidden payload fields:

- raw JWT/Clerk tokens;
- raw payment details;
- private profile data;
- partner settlement data;
- G2A/token/NFT/on-chain proofs;
- unsafe diagnostics.

## 10. Ledger / Points Contract

Action names:

- `referral_locked`;
- `referral_unlock`;
- `network_accrual_level_1`;
- `network_accrual_level_2`.

Contract:

- Points Service owns ledger writes.
- Ledger writes must be idempotent.
- `externalId` must be deterministic.
- Locked/available/network buckets must align with `docs/economy/points_policy_v1.md`.
- `referral_unlock` must not create duplicate available value.
- Network accrual rows must represent granted Points only.
- No ledger row creates cash-out, payout, partner settlement or external token obligation.

## 11. Connect / Wallet Projection Contract

Connect may show:

- granted ledger facts;
- Conditional Points;
- wallet buckets;
- referral tree/read model;
- safe activation status;
- safe explanation of VIP dependency.

Connect must not show:

- inactive potential network value as already granted;
- unimplemented unlock/accrual as active runtime;
- referral mechanics as financial result;
- unlimited depth;
- payout, settlement or cash-out semantics.

Wallet wording must remain participation-oriented:

- Points с условиями;
- Points за активность приглашённых;
- участие сети;
- вклад в рост экосистемы;
- активный VIP-период.

## 12. Anti-Abuse / Safety Guardrails

Policy guardrails:

- maximum referral reward depth is 2;
- no unlimited network depth;
- no self-referral;
- no duplicate relation reward;
- no duplicate unlock;
- no accrual from invalid, revoked or abuse-flagged users;
- no accrual without required active VIP entitlement;
- idempotency is required for every unlock/accrual write;
- audit evidence is required for future implementation;
- suspicious patterns can be reviewed by a future abuse policy.

Restricted semantics:

- no financial-return framing;
- no platform obligation framing;
- no payout/cash-out framing;
- no partner-settlement framing;
- no MLM framing.

## 15. Recommended Future Implementation Slices

Future slices:

- referral unlock event design;
- direct referral activity accrual design;
- second-level referral conditional grant design;
- second-level activity accrual design;
- wallet projection alignment;
- Connect copy guard;
