# Go2Asia — Pipeline Overview  
Главный конвейер мультиагентной разработки

Этот документ описывает **единый end-to-end поток разработки**, которым руководствуется Оркестратор и все ИИ-агенты в процессе создания функциональности для Go2Asia.

Pipeline определяет обязательную последовательность:  
**Требования → Архитектура → План → Разработка → Тестирование → Security → Документация → Релиз**,  
и включает обязательные точки ревью (review-mode), описанные в `review_pipeline.md`.

---

# 1. Цель пайплайна
Обеспечить:
- предсказуемость разработки,
- структурированность всех артефактов,
- отсутствие архитектурных и логических дыр,
- корректное auto-routing агентов,
- обязательный контроль качества через review-режимы,
- отслеживаемость всех решений через ADR.

Pipeline является «конституцией» процесса разработки.

---

# 2. Общая схема пайплайна

```
Запрос → Аналитика (ТЗ) → Архитектура → Планирование → Разработка → Тесты → Security → Документация → Релиз
                     ↑review↑        ↑review↑         ↑review↑      ↑review↑
```

Каждый переход к следующему этапу разрешён **только после прохождения ревью**, см. `review_pipeline.md`.

---

# 3. Подробный конвейер

## Этап 1 — Получение задачи
Оркестратор:
- фиксирует задачу,
- определяет область проекта (модуль/сервис),
- находит связанные ADR,
- выбирает агента через auto-routing.

**Выход:** постановка задачи.

---

## Этап 2 — Анализ требований (ИИ-аналитик)
Аналитик:
- уточняет детали у пользователя,
- формирует ТЗ,
- определяет функциональные и нефункциональные требования,
- определяет критерии приёмки.

**Выход:** файл ТЗ (`docs/modules/*/tz.md` или `docs/backend/*/tz.md`).

### 🔍 Обязательное действие:
Запускается **TЗ-review (review-mode)** у аналитика.  
→ Файл ревью: `docs/reviews/tz/review_<date>.md`

---

## Этап 3 — Архитектура (ИИ-архитектор)
Архитектор:
- анализирует ТЗ,
- проектирует структуру микросервисов,
- проектирует API и контракты,
- проектирует модели данных,
- проверяет совместимость с ADR,
- формирует схемы взаимодействий.

**Выход:** архитектурный документ.

### 🔍 Обязательное действие:
Запускается **Architecture-review**.  
→ Файл ревью: `docs/reviews/architecture/review_<date>.md`

---

## Этап 4 — Планирование (ИИ-планировщик)
Планировщик:
- декомпозирует функциональность на задачи,
- определяет зависимости,
- распределяет задачи между FE/BE/DevOps,
- формирует roadmap или sprint-план,
- формирует критерии завершённости этапа.

**Выход:** план (`docs/plans/phase_XXX.md` или `docs/plans/sprint_XXX.md`).

### 🔍 Обязательное действие:
Запускается **Plan-review**.  
→ Файл ревью: `docs/reviews/plans/review_<date>.md`

---

## Этап 5 — Подготовка инфраструктуры (DevOps-агент)
DevOps:
- готовит окружения,
- настраивает CI/CD,
- создаёт сервисы / функции / workers,
- обновляет миграции,
- обеспечивает доступ к переменным окружения.

**Выход:** рабочая инфраструктура.

> Если инфраструктурный шаг меняет архитектуру сервисов → требуется повторное Architecture-review.

---

## Этап 6 — Разработка (Frontend + Backend)

Разработка состоит из двух параллельных направлений,
но для фронтенда существует обязательная внутренняя последовательность.

---

### 6.1 UX/UI Design Authority (Frontend Dev sub-mode)

Перед реализацией UI Frontend Dev обязан:

- зафиксировать визуальную спецификацию (например, через `.pen` файл в Pencil);
- определить layout и структуру страницы;
- определить ключевые состояния компонентов;
- свериться с дизайн-токенами и UI-kit.

На этом этапе код не пишется.
Это подэтап внутри роли Frontend Dev.

---

### 6.2 Frontend Implementation

После утверждения визуальной спецификации:

- реализуются компоненты и страницы;
- производится интеграция с SDK/API;
- соблюдается соответствие `.pen` спецификации;
- проводится внутренняя проверка на консистентность UI.

---

### 6.3 Backend Implementation

Параллельно или независимо:

- реализуются API;
- добавляется бизнес-логика;
- обновляются модели данных;
- обновляется OpenAPI.

---

### 🔍 Обязательное действие:

Перед merge запускается **Code-review**
(Backend Dev + QA + Security в совместном review-mode).
→ Файл: `docs/reviews/code/review_<date>.md`

---

## Этап 7 — Тестирование (QA)
QA-агент:
- пишет unit, integration, e2e тесты,
- проводит тест-прогоны,
- фиксирует баги,
- проверяет критерии приёмки из ТЗ.

**Выход:** отчёт о тестировании.

> При выявлении ошибок — возврат на Этап 6.

---

## Этап 8 — Security Review (Security-агент)
Security-агент:
- анализирует использование токенов,
- проверяет доступы и права,
- выявляет уязвимости в сервисах и API,
- проверяет ошибки конфигурации.

**Выход:** security-отчёт.

> Критические проблемы → возврат на Этап 6.

---

## Этап 9 — Документация (Tech Writer)
Технический писатель обновляет:
- README модулей,
- API документацию,
- описание архитектуры,
- инструкции по деплою,
- CHANGELOG (если требуется).

---

## Этап 10 — Завершение и релиз
Оркестратор:
- проверяет, что все обязательные ревью пройдены,
- проверяет тесты и документацию,
- формирует итоговый отчёт,
- подтверждает завершение задачи.

---

# 4. Инварианты пайплайна

1. **Нельзя переходить к следующему этапу без прохождения ревью.**  
2. **Все решения фиксируются через ADR.**  
3. **ТЗ → Архитектура → План → Реализация должны быть консистентны.**  
4. **Каждый артефакт = файл в docs.**  
5. **Cursor обязан использовать auto-routing.**  
6. **Оркестратор является единственной точкой управления процессом.**

---

# 5. Где создаются артефакты

| Элемент | Путь |
|--------|------|
| ТЗ | `docs/modules/*/` или `docs/backend/*/` |
| Архитектура | `docs/architecture/` или `docs/backend/*/architecture.md` |
| План | `docs/plans/` |
| Ревью ТЗ | `docs/reviews/tz/` |
| Ревью архитектуры | `docs/reviews/architecture/` |
| Ревью плана | `docs/reviews/plans/` |
| Ревью кода | `docs/reviews/code/` |
| ADR | `docs/decisions/` |

---

# 6. Pipeline как часть мультиагентной системы

Pipeline — это основа:
- auto-routing задач,
- последовательности работы агентов,
- review-обязательности,
- контроля качества,
- принятия архитектурных решений.

Он позволяет масштабировать разработку, не теряя устойчивости.

---

# 7. Заключение

Этот pipeline — ядро всего процесса разработки Go2Asia.  
Он связывает работу всех агентов, обеспечивает прозрачность, контроль качества и предсказуемость релизов.

Оркестратор и Cursor ОБЯЗАНЫ следовать этому пайплайну при выполнении любых задач.
