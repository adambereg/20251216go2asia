# Auto Routing Rules (Правила автоматического маршрутизации агентов)

Этот документ описывает **когда** и **кого** Оркестратор должен вызывать автоматически при различных типах задач.

Главная цель авто-роутинга — снять нагрузку с Оркестратора на принятие повторяющихся решений.

---

# 🧭 Основные типы задач и соответствующие агенты

## 1. “Новая функциональность”
Маршрут:
1. requirements_analyst  
2. architect  
3. planner  
4. devops (если требуется инфраструктура)  
5. backend_dev + frontend_dev (параллельно)  
6. qa  
7. security  
8. tech_writer  

---

## 2. “Новый модуль”
То же, что новая функциональность, но devops запускается всегда.

---

## 3. “Дополнение существующего модуля”
Если изменяется:

### 3.1 Только UI
- только UI → frontend_dev (UX/UI sub-mode) → frontend_dev (implementation) → QA → tech_writer

### 3.2 Только API
- только API → backend_dev → QA → security → tech_writer

### 3.3 API + UI
- API + UI → frontend_dev (UX/UI sub-mode) → frontend_dev (implementation) + backend_dev (параллельно) → QA → security → tech_writer

Архитектор вызывается только если:
- меняется структура данных,
- требуется новый сервис,
- API ломает старую совместимость.

> Примечание: UX/UI sub-mode является внутренним режимом роли frontend_dev и обязателен при задачах, затрагивающих layout/структуру/компоненты UI (см. roles/frontend_dev.md).

---

## 4. “Исправление багов”
Маршрут:
1. backend_dev или frontend_dev (в зависимости от зоны)
2. qa
3. (опционально) security — если баг относится к безопасности

---

## 5. “Архитектурное изменение”
1. architect  
2. planner  
3. devops (если требует изменений в инфраструктуре)  
4. backend_dev + frontend_dev  
5. qa  
6. security  
7. tech_writer  

---

## 6. “Проблемы безопасности”
1. security  
2. backend_dev / devops — исправление  
3. qa (регресс)  
4. security (повторная проверка)  

---

# 🧩 Правила приоритета маршрутизации

## Приоритет 1: Аналитик  
Если задача непонятна → всегда вызывается requirements_analyst.

## Приоритет 2: Архитектор  
Если задача затрагивает структуру данных или поведение сервисов → architect.

## Приоритет 3: Планировщик  
Если меняется архитектура → planner.

## Приоритет 4: DevOps  
Если требуется новая инфраструктура.

## Приоритет 5: Разработчики  
Только после ясного ТЗ + архитектуры.

## Приоритет 6: QA  
После каждого значимого изменения кода.

## Приоритет 7: Security  
После QA или при изменении критических областей.

## Приоритет 8: Tech Writer  
Всегда последним этапом.

---

# 🎯 Итого
Auto-routing позволяет Оркестратору:
- работать по предсказуемой схеме,
- не пропускать важные этапы,
- не вызывать лишних агентов,
- экономить контекст и ускорять работу,
- обеспечивать качество и стабильность разработки.
