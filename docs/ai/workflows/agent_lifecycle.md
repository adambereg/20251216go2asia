# Agent Lifecycle (Жизненный цикл ИИ-агентов Go2Asia)

Документ описывает, как любой агент системы должен работать от момента вызова Оркестратором до предоставления результата.

---

# 🧬 Общий жизненный цикл агента

## 1. Инициализация
Оркестратор:
- запускает агента;
- передаёт входные данные (ТЗ, архитектуру, план и т.п.);
- указывает задачу и формат результата.

Агент:
- подтверждает получение данных;
- читает только относящуюся к делу информацию;
- формирует внутренний план выполнения.

---

## 2. Обработка задачи
Каждый агент должен:
- следовать своему роли-профилю из `roles/`,
- не выходить за рамки своих обязанностей,
- соблюдать формат вывода.

Если данных недостаточно → агент просит уточнение у Оркестратора.

---

## 3. Валидация результата
Перед тем как агент вернёт результат, он должен проверить:

- соответствует ли вывод задаче;
- нет ли логических противоречий;
- соблюдён ли формат;
- не нарушены ли ограничения роли.

---

## 4. Возврат результата Оркестратору
Агент должен вернуть:
- итоговые данные,
- краткое резюме,
- перечень использованных файлов (если есть),
- список рисков или “неполных областей”.

---

## 5. Возможная итерация
Если Оркестратор видит:
- неполноту,
- ошибки,
- отклонение от требований,
— агент запускается повторно.

---

# 📌 Особые требования к агентам

## Запрещено:
- менять архитектуру без указания,
- менять ТЗ без роли аналитика,
- писать код в ролях, не связанных с разработкой,
- генерировать тесты в роли разработчика,
- нарушать формат вывода.

## Обязательно:
- работать строго в своей роли,
- минимизировать домыслы,
- быть детальными, но не избыточными,
- сообщать, если решение невозможно без дополнительных данных.

---

## Дополнение: Sub-mode внутри роли (Embedded Modes)

Некоторые роли могут иметь внутренние режимы выполнения (sub-mode),
не создающие нового агента, но меняющие порядок действий внутри задачи.

### Пример: Frontend Dev → UX/UI Design Authority (Embedded)

Если задача относится к UI (layout, компоненты, визуальная структура),
Frontend Dev обязан:

1. Перейти в UX/UI sub-mode.
2. Зафиксировать визуальную спецификацию (например, через `.pen` файл в Pencil).
3. Только после этого перейти в implementation-mode (написание кода).

Важно:
- Sub-mode не является отдельной ролью.
- Ответственность остаётся внутри исходного агента.
- Lifecycle не меняется, меняется порядок выполнения шагов.

---

### Порядок работы в sub-mode

1. Инициализация (получение задачи).
2. UX/UI sub-mode (если триггер выполнен).
3. Implementation-mode.
4. Возврат результата Оркестратору.

---

### Ограничения

- Sub-mode не может менять архитектуру.
- Sub-mode не может менять ТЗ.
- Sub-mode не может инициировать новые роли.
- Все изменения должны соответствовать pipeline и auto-routing.

---

# 🧠 Принцип “Single Responsibility Agent”
Каждый агент выполняет **только одну роль**.

Пересечение зон ответственности исключено.
