## Search Conventions v1 (единый стандарт параметров поиска/фильтров)

**Статус**: standard v1  
**Область**: все модули (Atlas, Pulse, Blog/Media, Guru, Rielt, RF, Space, User, …)  
**Цель**: единые конвенции query-параметров, URL-sync политики и формы facets.  
**Ограничение**: стандарт описывает целевое именование. Если в коде уже есть другие имена — они считаются legacy до миграции.

См. также:
- `docs/decisions/search_strategy.md`

---

## 1) Единый параметр текстового поиска

### 1.1 Норма (v1)

- **`q`** — единственный рекомендуемый параметр текстового поиска во всей экосистеме.

### 1.2 Legacy

- **`search`** — legacy/нежелательный.  
  Если где-то уже используется `search`, в документации:
  - описываем текущее поведение как AS IS,
  - но указываем, что целевое имя — **`q`**.

---

## 2) Рекомендуемая схема query-параметров (v1)

### 2.1 Общие правила именования

- Query-параметры — **camelCase**.
- Явно различаем:
  - `...Id` — внутренний идентификатор (UUID/строка),
  - `...Slug` — человекочитаемый slug (если это реально используется).

Пример: `countryId=...` или `countrySlug=thailand`.

### 2.2 Базовые параметры (универсальный набор)

- **`q`**: строка — текстовый поиск.
- **`categoryKey`**: ключ taxonomy (derived metadata) для смысловой навигации/фильтрации (Atlas v1).
- **`countryId`**, **`cityId`**: фильтрация по географии (ID).  
  Если используется slug: **`countrySlug`**, **`citySlug`** (не смешивать `Id` и `Slug` в одном параметре).
- **`kind`**: тип/подтип сущности внутри домена.  
  Обоснование выбора: в текущем коде Atlas Places уже использует `kind` как параметр API, поэтому v1 фиксирует **`kind`** как стандарт.
  - `type` зарезервировать для “типа сущности” в агрегированных выдачах (например, `place/event/article`), либо не использовать вовсе, чтобы не путать с `kind`.
- **`tags`**: теги, формат **CSV**: `tags=tag1,tag2,tag3`
  - Причина: проще и единообразнее для фронта, и легко валидировать.
  - Альтернатива (`tags=tag1&tags=tag2`) допускается только если API явно так реализован; по умолчанию в docs писать CSV.
- **`sort`**: режим сортировки (строка/enum), например:
  - `sort=recommended`
  - `sort=newest`
  - `sort=distance`
  - `sort=rating`
- **Пагинация** (предпочтение v1): **cursor-based**
  - `limit` — размер страницы (например 20–100, с max на стороне API)
  - `cursor` — курсор следующей страницы (opaque string)
  - Примечание: если текущий API использует `page/pageSize`, это фиксируется как AS IS; v1 целевой стандарт — `limit/cursor`.
- **Булевые фильтры**: использовать “1/0”:
  - `withPhotos=1` (вместо `onlyWithPhotos`)
  - `rfOnly=1`, `openNow=1` и т.п.
  - Причина: проще для URL и совместимо с HTML-формами.

### 2.3 Примеры

- Atlas places (целевой вид):
  - `?q=coffee&countryId=...&cityId=...&kind=business&tags=wifi,outlets&withPhotos=1&sort=nameAsc&limit=50`
- Pulse events (целевой вид):
  - `?q=tech&cityId=...&tags=meetup,community&sort=startsAtAsc&limit=50`

## 3) URL-sync policy (когда сериализуем фильтры в URL)

### 3.1 Обязательная URL-синхронизация (v1)

Следующие страницы **должны** сериализовать активные фильтры в URL (shareable links, back/forward, воспроизводимость):
- Atlas Places
- Pulse
- Guru
- Rielt Search Results

### 3.2 Допустимая локальная фильтрация без URL (v1)

Если страница — “локальный каталог” с малой выборкой (моки/демо) и без требования шаринга:
- RF каталоги (партнёры/ваучеры) — могут оставаться с локальным state (AS IS), но при переходе на real data желательно перейти к URL-sync по правилам выше.

---

## 4) Facets (если используются)

### 4.1 Общий shape ответа (v1)

Если API/клиент формирует facets, использовать следующий shape:

- `facets.tags[]`: `{ key: string, count: number }`
- `facets.categories[]`: `{ key: string, label?: string, count: number }`

Примечания:
- На текущем этапе facets могут вычисляться **на клиенте** (как в Atlas Places).
- Позже facets могут вычисляться **на сервере/в движке**, но shape остаётся тем же.

---

## 5) UX практики (v1)

- **Debounce для `q`**: 250–400ms, значение по умолчанию — **300ms**.
- **Minimum query length**: рекомендуется **2** (опционально по модулю).
- **Нормализация текста**:
  - `lowercase`
  - `trim`
  - (опционально) нормализация пробелов и диакритики по требованиям домена.
