# ADR-0023: Введение Geo Layer (geo-module → geo-service) и правила границ

**Статус:** Accepted / Strategic guardrails  
**Дата:** 2026-02-11  

## Контекст

Экосистема Go2Asia эволюционирует от “карты Atlas” к набору geo-aware доменов: Guru (персонализация nearby), Quest (маршруты/триггеры/proximity), Space (UGC/лайв-активность/heatmaps), Rielt (недвижимость), Pulse (события), Connect (экономические сценарии, привязанные к гео).

Без платформенного Geo Layer возникают системные проблемы:
- распад DTO и разные допущения по координатам/радиусам/viewport;
- дублирование координат и конфликт “кто правит гео-поля” между доменами;
- перенос гео-композиции в UI и рост интеграционного долга;
- невозможность устойчиво масштабировать “nearby + много слоёв + (почти) real-time”.

Стратегический документ: `docs/architecture/geo_architecture_evolution.md`.

## Решение

Ввести **Geo Layer** как платформенную способность и зафиксировать его границы:
- На ранних этапах допускается реализация как **geo-module внутри `content-service`** (организационный компромисс).
- При росте нагрузки/требований Geo Layer выделяется в **отдельный `geo-service`** без ломки клиентов, потому что внешний контракт остаётся стабильным.

Ключевой принцип: Geo Layer — **инфраструктурный spatial-движок**, а не бизнес-сервис.

## Geo Contract v1 — обязательный

**Норма платформы:** все гео-представления, используемые на карте (любой модуль экосистемы), **обязаны соответствовать `Geo Contract v1`**.

Запрещено:
- вводить “временные DTO” для карты под отдельный модуль;
- добавлять критичные поля логики в формат карты без версионирования.

Допускается:
- расширение через `meta` (ограниченное по размеру);
- введение новой версии контракта только как платформенное решение (v2+) с миграционным планом.

## Ownership (источник истины) — фиксируется заранее

Geo Layer не владеет доменными сущностями и не является источником истины для координат.

Канонические владельцы:
- Atlas / `content-service`: `countries/cities/districts/places`
- Pulse: `events`
- Quest: `quest_points/routes`
- Space: `user activity` / `UGC` слои (с privacy-политиками)
- Rielt: `properties`

Роль Geo Layer:
- агрегация слоёв;
- spatial-индексация;
- кэширование;
- производные проекции для быстрого чтения.

Любая правка координат возвращается в домен-владелец.

## Границы ответственности Geo Layer (anti-god-service правила)

Geo Layer **должен**:
- предоставлять стандартные гео-запросы (viewport/nearby/слои);
- обеспечивать скорость чтения через индексацию/кэш/проекции;
- выдавать данные только в Geo Contract v1 (или версионированно).

Geo Layer **не должен**:
- хранить и “править” первичные координаты доменных сущностей;
- содержать доменную бизнес-логику (правила Guru/Pulse/Quest/Rielt/Space);
- становиться “единым API всех доменов” с бизнесовыми ответами;
- принимать решения о модерации/приватности вместо доменов (он может исполнять их ограничения, но не определять).

Правило проверки: если правило зависит от доменной семантики (например, “RF-партнёры выше в выдаче”, “квест засчитан”, “контент виден друзьям”) — оно **не** принадлежит Geo Layer.

## Триггеры выделения geo-service (момент обязательности)

Geo Layer становится обязательным выделенным `geo-service`, когда выполняются условия:
- кросс-доменные geo-запросы становятся основным UX (nearby/viewport объединяет 2+ домена);
- появляется пользовательское гео-состояние/событийность как продуктовая сущность (контекст/прогресс/триггеры);
- требуется real-time/частые обновления со своими SLA (Quest/Space);
- метрики geo-нагрузки устойчиво переходят в класс “Action/Mandatory”.

Конкретные метрики/пороги: `docs/architecture/geo_architecture_evolution.md` → “Триггеры миграции в geo-service”.

## Стратегия миграции без боли (module → service → gateway switch)

Принцип: внешний контракт стабилен, внутренняя топология меняется маршрутизацией.

- Зафиксировать Geo Contract v1 как единственный формат карты.
- Реализовать Geo Layer как geo-module внутри `content-service` (с явными границами и SLA).
- Подготовить интерфейсы “как сервис” (без утечек доменной логики наружу).
- Вынести модуль в отдельный `geo-service`.
- Переключить маршрутизацию на API Gateway (route switch + откат).
- Отключить legacy путь после стабилизации.

## Последствия

**Плюсы**
- единый язык гео-данных для всей экосистемы;
- предотвращение распада DTO и “временных костылей”;
- снижение интеграционного долга (UI/Guru не становятся компоновщиками доменов);
- защита от превращения Geo в god-service через явные границы.

**Минусы**
- потребуется дисциплина ownership и контрактов (особенно при росте доменов);
- появится дополнительный инфраструктурный контур (проекции/индексация/кэш), который нужно наблюдать и поддерживать.
