## Search Strategy (AS IS → TO BE, без обещаний “сервис уже есть”)

**Статус**: decision / стратегия (живой документ)  
**Область**: вся экосистема Go2Asia (frontend + backend + docs)  
**Цель**: привести описание поиска к реальному состоянию (AS IS) и зафиксировать эволюционный подход к развитию поиска без преждевременного выделения обязательного “Search Service”.

См. также:
- `docs/standards/search_conventions_v1.md` — конвенции query-параметров и URL-sync policy (v1)

---

## 1) AS IS (фактическое состояние в репозитории)

### 1.1 Backend search (единый `/search`) — не реализован

- В коде репозитория **не обнаружены** backend-эндпойнты уровня:
  - `GET /api/atlas/v1/search`
  - `GET /v1/search`
  - и аналогичные “универсальные” `/search` для доменных сервисов.
- В документации встречаются контракты `/search`, которые могут выглядеть как существующие. **До появления кода такие контракты должны считаться PLANNED / NOT IMPLEMENTED.**

### 1.2 Frontend: текущая реализация поиска/фильтрации — в основном client-side

Фактическая картина по модулям (обобщение):
- **Client-side filtering/search**:
  - текстовый матчинг в основном через `includes()` (без fuzzy),
  - часть страниц синхронизирует фильтры с URL, часть — хранит только в локальном состоянии.
- **Atlas Places** — смешанный подход:
  - часть фильтров уходит в API (`countryId`, `cityId`, `kind`, `limit`),
  - часть применяется на клиенте (например, фильтрация по `tags`, “категории из тегов”, `onlyWithPhotos`, клиентская сортировка).

### 1.3 Глобальный поиск в App Shell — заглушка

- В App Shell есть UI-элемент (кнопка/иконка) поиска, но функциональность открытия/ввода/результатов **не реализована** (TODO в коде).

## 2) TO BE (эволюционный подход без преждевременного “поискового сервиса”)

Ниже — стратегия развития поиска по этапам. Важно: это **направление**, а не утверждение, что что-то уже реализовано.

### Этап A — текущий / MVP: базовые фильтры + простой текстовый матчинг

Фокус:
- Быстрые итерации по UI и модели данных.
- Поиск и фильтры могут оставаться:
  - на клиенте (для моков/малых выборок),
  - частично на API (структурные фильтры: страна/город/тип и т.п.).

Ограничения этапа:
- Нет гарантий единой релевантности между модулями (каждый модуль может сортировать/ранжировать по-своему).
- Возможны различия в именах параметров, если не зафиксированы конвенции (см. v1 стандарт).

### Этап B — следующий: server-side search в доменных сервисах (там, где это нужно объёмом данных)

Когда объём данных/нагрузка требуют:
- Доменные сервисы добавляют server-side обработку:
  - `q` (простая строка) как минимум ILIKE/простой матчинг,
  - структурные фильтры и сортировки — на стороне API.
- Фронтенд постепенно перестаёт “тащить всё и фильтровать локально” (для больших выборок).

Важно:
- API остаётся **доменным** (Atlas/Pulse/Media/Rielt/User/… сами отвечают за свои сущности и правила).
- “Поиск” рассматривается как capability домена, а не как отдельный обязательный продуктовый сервис.

### Этап C — позже: подключение поискового движка (Meilisearch/OpenSearch) как инфраструктурного компонента

Когда появляется потребность в полнотекстовом поиске, автодополнении, скорости и расширенных фильтрах:
- Подключается поисковый движок (например, Meilisearch/OpenSearch) **как инфраструктурный компонент**.
- Доменные API остаются точкой входа для клиентов, а внутри могут:
  - проксировать запросы в движок,
  - или использовать Postgres FTS как промежуточный вариант.
- Индексация данных строится вокруг событий/пайплайнов доменных сервисов.

### Этап D — глобальный поиск: опционально фасад/агрегатор позже

Глобальный поиск по нескольким доменам (Atlas+Pulse+Media+…):
- возможен как **фасад/агрегатор** на позднем этапе,
- не обязателен как отдельный микросервис в MVP,
- может жить как слой агрегации (BFF/edge/гейтвей), когда появится реальная потребность и договорённости по контрактам.

## 3) Термины и границы (запрет двусмысленности)

### 3.1 “Search Service”

- **Запрещено** называть “Search Service” обязательным отдельным микросервисом в MVP.
- В документации термин “Search Service” допускается только как **поздняя опция** или инфраструктурный компонент (движок), но не как “уже существует”.

### 3.2 “Поиск”

В Go2Asia “поиск” = capability доменных модулей, реализуемая через:
- доменные API (server-side, когда нужно),
- клиентскую фильтрацию (когда допустимо),
- единые конвенции параметров и URL-политики.

### 3.3 Контракты `/search` в docs

- Любой `/search` endpoint, описанный в документации, **обязан** иметь явную маркировку:
  - **PLANNED / NOT IMPLEMENTED** — пока нет реализации в коде,
  - **IMPLEMENTED** — только если есть код + маршрут/хэндлер.
